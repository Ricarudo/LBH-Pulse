# Quote lifecycle implementation plan — Pulse 0.2

Date: 2026-09-25. Target implementation plan. The
[first-pass implementation report](0.2-quote-lifecycle-first-pass.md) records
what is implemented, staged, tested and still outstanding; the full lifecycle
cutover is not yet active.
The [second-pass report](0.2-quote-lifecycle-second-pass.md) adds frozen readers
and the tested new-record family transaction service, with explicit activation
requirements.
This is the implementation authority for this workstream. It refines the
[lifecycle proposal](0.2-lifecycle-state-model.md) and the
[database assessment](0.2-database-gap-analysis.md). Preserve the original
owner-supplied release design unchanged.

## 1. Objective, confirmed decisions and boundaries

Deliver a quote lifecycle in which every offer has a permanent identity,
sent commercial content is immutable, revisions are new linked Quote records,
and lists, home widgets and analytics distinguish opportunities from versions.

Confirmed by the owner:

| Decision | Selected behavior |
| --- | --- |
| Implementation boundary | Quotes, their UI/widgets/analytics, and request/project handoffs. Do not redesign all Request/Project/Billing states in this workstream. |
| Quotes list | One row per quote family, exposing its outstanding offer, draft and history. |
| Supersession | A replacement supersedes the previous offer when sent, not when drafted. |
| Internal review | Optional formal, content-bound review. A requested unresolved review blocks send. |
| Client acceptance | Always create/link the project in the same transaction; no new accepted-but-unlinked records. |
| Win rate | Accepted / (Accepted + Rejected + Expired), once per closed family; cancellations and superseded versions excluded. |
| Renewing closed opportunities | New family linked to the old one. Never reopen the original family or erase its outcome. |
| Pricing validity | Default 30 calendar days on send, overridable; expiry produces Needs Refresh rather than automatic closure. |

Implement lifecycle correctness using current financial calculations and
existing document storage. Full supplier management, Excel formula parity,
template/PDF generation, a general notification platform, licensing, themes
and comprehensive accounting are separate 0.2 workstreams. Provide exact
content/document references that those features can use later. Do not require
a not-yet-built PDF generator to send a quote.

## 2. State, persistence and transaction rules

### Identity and sources of truth

- Add `QuoteFamily` with stable base number, source request/project references,
  optional renewed-from family, revision sequence, current draft/offer/accepted
  version pointers and current family outcome projection. Constrain pointers
  to members of the same family. The family holds operational grouping, not
  shared mutable commercial content.
- Extend Quote with `familyId`, predecessor identity, content version,
  publication state, version outcome, frozen snapshot reference, readiness
  content version, draft deadline, follow-up date, valid-through date and
  snapshotted validity time zone. Keep Quote IDs/numbers permanent. Enforce
  unique family/revision number and at most one open draft per family.
- Add immutable, schema-versioned `QuoteContentSnapshot` records containing
  commercial identity, scope, lines, exact decimal finances, policy/provenance
  and referenced document IDs. Reviews and send bind to an exact snapshot and
  content version. Missing legacy evidence is explicit, not reconstructed
  from today's master data.
- Add `QuoteReview` submissions and decisions with reviewer, submitter,
  content identity, timestamps and reason. Preserve old submissions when
  content changes or reviews are cancelled.
- Extend the existing lifecycle event ledger with optional typed quote event,
  family/version/content/snapshot identity and operation identity. Emit each
  business transition once; keep generic Activity as audit presentation, not
  a second analytics source. Update materialized current-state projections
  atomically with their events. Existing non-quote ledger behavior remains.
- Persist idempotency records with a unique actor/action/key and request hash;
  return the original result on an identical retry and reject key reuse with
  a different payload. Mutation bodies include expected content version where
  commercial content or its publication is involved.

### State model

Publication is Draft or Sent. Preparation labels are Draft, In Review,
Changes Requested and Ready to Send; review/readiness records determine the
label, rather than a second independently writable review status. Mark Ready
records a successful existing send-validation check against the content
version. Approval of that version also marks it ready. A commercial edit
increments content version and invalidates readiness and approval.

Quote family outcomes are Accepted, Rejected, Cancelled or Expired. Individual
versions can additionally be Superseded, discarded drafts, or corrected send
records. These are version history, not additional family losses. Open/Closed
list grouping is derived. On Hold is an operational flag with reason and
optional resume date; it prevents preparation/send until explicitly resumed.
Follow-up and validity warnings remain visible while on hold.

Client acceptance is displayed as Accepted; internal review uses Approved.
Retain compatibility mappings for existing strings and never reinterpret old
client Approved events as internal review decisions.

### Allowed actions and edge cases

1. **Edit:** all commercial mutations lock family then Quote, recheck editable
   state and expected content version, update data/version and record financial
   value history when it changes. Include title, parties, scope, proposal notes,
   lines, calculation mode and selected commercial documents. Assignments,
   collaborators, follow-ups and comments are separate operational edits.
2. **Review:** optional until explicitly requested. Reviewer must be an active
   different user with `quotes:review`; bootstrap that permission for system
   Administrators and allow role administration to assign it. No self-approval.
   Pending, Changes Requested or stale approval blocks send. The submitter or
   reviewer may explicitly withdraw optional review with a required reason;
   record that event rather than silently bypassing review. Commercial edits
   after submission make that submission stale and require resubmission or
   explicit withdrawal. Operational edits do not invalidate it.
3. **Send:** validate current content/readiness/review in one transaction,
   create/reference its immutable snapshot, record sent time and validity,
   supersede the family's previous current offer, and point the family at the
   new offer. Require resume from hold first. Snapshot selected existing
   proposal/source-document IDs; do not treat arbitrary later uploads as part
   of the sent package. The action records that the user sent the offer; it
   does not claim automatic email delivery.
4. **Revise an open offer:** create a new Quote ID and new line IDs in the same
   family, with predecessor and optional prior-line references. Copy the
   original stored commercial values; preserve existing file references without
   copying binaries or reparenting documents. Reset send/outcome/review/readiness,
   generated-artifact association and resulting validity. Start its preparation
   deadline/follow-up blank; inherit assignee/collaborators, not open tasks.
   Require reason and origin: Client requested or Internal revision. Do not
   refresh catalog/directory data automatically. Return an existing open draft
   on duplicate attempts rather than create parallel drafts.
5. **Discard a draft revision:** record cancellation of that version. If an
   outstanding sent offer exists, the family stays open. If no offer remains,
   require the user to explicitly close the family or create another draft.
   Historical abandoned versions remain visible and numbers are never reused.
6. **Accept and hand off:** accept only the current, unclosed sent version with
   known unexpired validity. Older legacy offers lacking validity require a
   revision/send before new acceptance; already accepted legacy records remain
   accepted. Create a new project/original link or link an eligible existing
   same-client project as a change order using existing destination rules.
   Snapshot exact accepted scope/finances; close any sibling draft and pending
   review; update project budget once. Require both quotes and project write
   permissions. Any failure rolls back acceptance and handoff together.
7. **Close:** Rejected applies to an outstanding sent offer; Cancelled/Expired
   may close an open preparation or sent family, with a reason. Close remaining
   open draft/reviews and operational follow-ups through recorded actions.
   Pricing expiry alone never creates a terminal event. Reject stale actions
   against superseded or closed versions.
8. **Renew closed work:** Copy to new quote creates a new family/base number
   linked to the closed family. Preserve the old decision and reporting. After
   acceptance, changes use a separate project-linked change-order family;
   accepted scope cannot be silently replaced.
9. **Correct mistaken send:** retire ordinary Undo Sent. An administrator can
   record a reasoned erroneous-send correction only before acceptance and when
   no later sent replacement exists, keeping its original frozen record and
   evidence. Create a replacement draft or return the existing draft. Do not
   automatically resurrect an older superseded offer. A real withdrawn offer
   is cancellation, not an erased send event. Corrections adjust effective
   reporting from their event time; they never delete raw historical events.

Freeze valid-through as a calendar date and the workspace time zone at send;
default to local send date + 30 days, valid through that day's end. Needs
Refresh begins at the next local midnight. Store event instants with explicit
time-zone semantics. New preparation/follow-up fields are calendar dates.
Existing dueDate maps only to preparation; stop live request-date fallback for
new versions. Existing sent records retain unknown validity rather than
receiving invented historical dates.

Implementation defaults beyond the confirmed choices: no self-approval; reject
acceptance of superseded, expired or unspecified-validity offers; require a
fresh revision/send instead. Archive only closed families through ordinary
UI actions. Archiving never removes their historical analytics facts. These
defaults are explicit so implementation does not invent different policies.

Referenced commercial documents cannot be ordinarily soft-deleted or replaced.
Keep their exact versions available to authorized historical readers. Directory
navigation can remain live, but frozen commercial presentation must use the
snapshot. Preserve internal financial permissions across APIs and exports.

## 3. APIs and UI/UX

### Interfaces

- Keep `/quotes/:id` as an exact-version address. Add family summary/list/history
  reads; retain the existing list response for compatibility and expose family
  mode explicitly. Old `?record=` URLs continue to resolve exact records.
- Extend revision creation to return `{quote, familyId, sourceQuoteId}` where
  `quote.id` is the new record. Resolve the legacy revision endpoint through an
  adapter for existing QuoteRevision JSON and new version records.
- Add explicit ready/review/decision/close/renew/correction operations. Extend
  mark-sent with expected content version, valid-through date, optional
  follow-up and selected document IDs. Route acceptance through a combined
  accept-and-handoff command returning Quote plus Project/link. Keep the old
  approve route as a compatibility alias to the same guarded transaction.
- Stop accepting lifecycle transitions through generic Quote PATCH. Return
  clear 409 conflicts for stale content, frozen commercial writes, duplicate
  active drafts, superseded acceptance and expired acceptance, including the
  current version/draft link when the user can access it. Remove the reopening
  behavior from the old undo-sent route and return a replacement-action error.
- Shared contracts expose family/version IDs, derived preparation/group,
  publication/outcome, current-offer/draft references, readiness/review,
  frozen state, explicit date kinds and server-calculated allowed actions.
  Add family/version/unit identity to analytics drilldowns and widget items.

### Quotes list and workspace

- Main list tabs: Open, Working, Awaiting response, Closed and All. Keep My
  work as a scope/view. Closed offers outcome filters for Accepted, Rejected,
  Cancelled and Expired. History is an expanded family section, not a row that
  inflates the main count. Working and Awaiting response may both match a family
  with a sent offer and a draft; each view still counts that family once.
- Show the current offer number/value and draft number/value separately when
  both exist. Label the primary figure Offer value or Draft estimate. Never
  add the two. Family search covers every version; an exact old quote-number
  match opens that version, not whichever is newest.
- Retain established list controls, URL filters, user view/sort preferences,
  client context, keyboard behavior and mobile bottom sheets. Migrate old
  status/view parameters with explicit mappings. Apply filtering before totals
  and pagination; no filtering of only the loaded page.
- Header shows exact quote number, family/history navigation, lifecycle badge,
  outcome and separate attention chips. A frozen banner explains what is locked
  and provides Create revision. Replace the single status dropdown with named
  actions and an outcome/close menu. Accepted versions show their project link.
- Separate commercial content from operational follow-ups. Preserve familiar
  workspace tabs; add a review panel and family history showing reviewer/client
  decisions, send, supersession, correction and handoff against exact versions.
- Revision dialog previews source/version and copied/reset fields, requires
  origin/reason, then navigates to the new draft. Existing-draft conflicts offer
  Open draft. Send dialog previews customer total, frozen parties/scope summary,
  review result, validity, included documents and previous offer to supersede.
- Acceptance dialog always chooses/validates the project destination. One
  submit records both actions. Legacy accepted-but-unlinked records display
  Repair project handoff; fixing the link must not create a second win.
- Reuse responsive components and semantic tokens. Verify 390/768/1440 px,
  200% zoom, keyboard focus/return, screen-reader labels, non-color state cues,
  empty/error/loading states and stale-action recovery. Do not redesign the
  whole application shell in this workstream.

### Home widgets

Reuse the existing five widget IDs and saved placement preferences.

| Widget | New quote behavior |
| --- | --- |
| Attention summary | Count distinct actionable families per bucket, not versions. A family can appear in different buckets but only once within each. Needs Attention is the union. Include review requests, preparation overdue, follow-up due, Needs Refresh, missing follow-up and legacy handoff repair. |
| Work queue | One family entry with explicit child actions for draft preparation/review and sent-offer follow-up. Display both when relevant. Sort using the earliest applicable actionable date, then existing priority/stable identity; do not lose undated attention actions. Preserve Mine/Team/All and complete-step actions against the actual task. |
| Upcoming dates | Separate preparation, follow-up, validity and explicit step dates with exact-version links. Multiple dates are legitimate schedule entries; labels explain that schedule entries are not opportunity counts. Never show an old preparation deadline as a sent-offer or project deadline. |
| Recent activity | Append-only, exact-version actions with family links; show revision creation separately from new-opportunity creation and supersession separately from losses. |
| Module health | Quotes count = distinct open families, including sent offers. Detail shows working/awaiting-response/needs-refresh subsets, explicitly overlapping where necessary. New accepted records leave quote work and appear under their project. |

Scope/filter before grouping and before the existing display caps. Select only
authorized/scoped actions, then deduplicate family counts. All five widgets,
quote list counts and client work lists use one backend lifecycle projection.
Review assignments surface through work queue plus existing update/mention
mechanisms; a general notification service is not required here.

Send and handoff dialogs require a disposition for each affected open step:
complete, cancel or retain/transfer. Suggest completion for preparation steps
at send and sales follow-ups at acceptance; do not silently classify ambiguous
legacy steps. Retained follow-ups stay on their source offer until resolved or
explicitly transferred. Execution transfers create project-owned steps with
source provenance and resolve the old step as transferred, preserving its
history. Never reparent an old activity or duplicate an unresolved task. Remove
implicit request→quote→project current-step fallback for new transitions.

## 4. Analytics contract and worked example

Implement a common quote facts adapter used by KPI cards, charts, comparisons,
tables and exports. Each fact identifies family, exact version, event time,
financial snapshot, attribution and evidence quality. Adapt legacy ledger and
QuoteRevision evidence without emitting duplicate facts. Preserve existing
non-quote analytics and maintain compatibility aliases for old metric IDs.

| Metric | Required definition |
| --- | --- |
| Opportunities created | Families first created within the selected period. A revision never increments this. Renewed closed work is a new family. |
| Open pipeline | As of period end, one pre-tax value per open family: outstanding sent offer first, otherwise active draft. A newer unsent draft cannot replace the current offer's value. Held/Needs Refresh families stay included with separate breakdowns. Closed families contribute zero. |
| Win rate | Families closing in period as Accepted / (Accepted + Rejected + Expired). Cancelled, corrected sends and superseded/discarded versions are excluded. Zero eligible decisions returns unavailable, not 0%. |
| Accepted contract value | Sum exact accepted pre-tax offer snapshots at acceptance; label it contract value, not invoiced revenue or cash. Each family contributes once. |
| Average accepted value | Accepted contract value / accepted families with complete required evidence; preserve unavailable/partial quality semantics instead of treating unknown as zero. |
| Accepted estimated margin | (Sum accepted pre-tax sales − Sum accepted estimated cost) / Sum accepted pre-tax sales. Revenue-weighted, not average of quote percentages. Exclude tax and retain existing zero-cost/unknown-evidence rules. |
| Offers sent | Distinct successfully sent version identities in period, not family count and not delivery retries. Label any gross sum of sent offer values as version activity; do not present it as pipeline or sales. |
| Revisions created | New same-family revision drafts created in period, split Client requested/Internal. Renewals of closed families are not revisions. |
| Client revision return rate | Among versions sent in the selected period, fraction with a recorded client-requested revision by the selected period end. Internal corrections/revisions do not count. Preserve a reason-origin quality flag for ambiguous legacy records. |
| Revisions per affected family | Revision creations in period / distinct families with a revision creation in period. Label the affected-family denominator; zero affected families is unavailable. |
| Request-to-quote time | Original request received → first linked family creation, once per conversion. Revisions and renewed opportunities do not restart or add conversion samples. |
| Sales cycle time | First send within that family → final family decision, when both are known. Also expose offer-response duration from the decided version's send; label them separately. |
| Project budget | Accepted original baseline plus accepted change-order increments, each exact version linked once. Draft revisions and superseded offers never change budget. |

All quote family metrics include new-work and change-order families by default,
with an explicit All/New work/Change orders filter and breakdown. Change-order
acceptance adds its increment to project budget but not another project count.
Do not sum pipeline, project budget and invoiced amounts as independent revenue.
Billing issue/paid/AR rules remain unchanged.

Use the workspace business time zone for period boundaries. Capture event-time
client/owner/trade classification; live directory/assignment edits must not
rewrite historical decisions. Current operational lists use current assignees.
Historical pipeline uses the value and lifecycle events known by that period
end, not today's row. Future revisions/sends cannot alter earlier-period
pipeline. Trade series retain the existing overlap notice for multitrade work.
Unknown historical state, dates, currency meaning or costs stay flagged through
existing quality metadata; never silently substitute current values.

Every card's formula popover states unit, period/as-of basis, denominator,
inclusions/exclusions and tax basis. Drilldowns use the identical facts and
filter set as their card and link to exact versions, including legacy history.
Sorting occurs before server pagination. Keep role/financial redaction
consistent for cards, charts, details and exports.

Acceptance fixture (amounts pre-tax):

| Action | Open families | Pipeline | Sent versions | Accepted value / project budget |
| --- | --- | --- | --- | --- |
| Send Q-104 for 1,000 | 1 | 1,000 | 1 | 0 / no project |
| Draft R1 for 1,200 | 1 | 1,000 | 1 | 0 / no project |
| Send R1 | 1 | 1,200 | 2 | 0 / no project |
| Accept R1 and create project | 0 | 0 | 2 | 1,200 / 1,200 |

This is one opportunity, one revision, two sent versions and one win. If R1's
captured cost is 700, estimated accepted margin is 41.67%. Adding one rejected,
one expired and one cancelled family gives win rate 1/3 = 33.33%, not 25%.
A later accepted 200 change order changes project budget to 1,400 without
changing its original 1,200 baseline or creating another project.

## 5. Delivery order, migration and acceptance gates

Implement in dependency order; each stage includes its focused tests.

1. **Contracts and characterization:** freeze the definitions above in shared
   types/policy functions and fixtures. Record current quote/dashboard/analytics
   behavior, legacy quality handling and permission boundaries. Extract focused
   lifecycle/projection services instead of expanding the existing monolith.
2. **Additive persistence and adapters:** add family/content/review/idempotency
   structures and ledger fields; preserve all original columns/IDs/statuses and
   `updatedAt` values during backfill. Each current Quote starts its existing
   family; map prior QuoteRevision JSON as read-only historical members, not new
   rows in protected Quote/QuoteItem tables. Preserve legacy URLs. Snapshot
   completeness is assessed from original evidence only.
3. **Guarded commands and handoffs:** implement new identities, locks, optional
   review, freezing, supersession, closure/renewal and atomic acceptance. Apply
   mutation guards to every entrypoint, including imports, bulk/context edits,
   proposal notes and document operations. Update Request source navigation and
   exact ProjectQuote links without changing their broader state models.
4. **UI and projections:** switch family lists, exact-version workspaces,
   client work/search links, all five widgets and date/task ownership together.
   Update analytics facts, formulas, comparison periods and drilldowns before
   enabling writes. No mixed old/new revision writers against the same family.
5. **Upgrade rehearsal and activation:** restore a representative 0.1.2 backup
   including MinIO, run additive migrations and existing updater preservation/
   runtime-grant checks, compare old-report fixtures through the compatibility
   adapter, then run new-flow acceptance. Publish 0.2 source/target migration
   metadata. Deploy under maintenance and activate the new lifecycle as a single
   installation capability after all readers are compatible. Disabling it stops
   new lifecycle writes while preserving historical reads; it must not restore
   the unsafe old writer. Recovery after migration uses the verified restore
   procedure, not application downgrade against new data.

Legacy histories may contain multiple decisions under the old in-place
revision model. Keep their established ledger resolution for pre-cutover
periods, label them legacy, and do not invent new families/episodes. New family
outcome rules apply to post-cutover commands. A renewed closed legacy quote
gets a new family. Backfill events/maps only when original evidence proves
the association. Preserve old missing-project Accepted records as repair cases;
repairing a link does not create another acceptance event.

Do not relax updater hashes. New columns/tables can be backfilled without
changing protected original columns/row sets. Expanding old historical JSON
into additional Quote rows is explicitly deferred. Extend backup/restore and
future-upgrade preservation coverage for the new commercial tables. Do not
replay legacy migrations, reset the database or use db push.

Required verification:

- Pure policy/contract tests for groups, transitions, dates, review invalidation,
  family representative selection and every metric formula/denominator.
- Isolated PostgreSQL integration tests for duplicate requests, simultaneous
  draft creation, edit versus send, send versus acceptance, stale review,
  superseded/expired acceptance, atomic project creation/link and duplicate CO
  approval. Verify original quote IDs, numbers, snapshots and files stay stable.
- Master-data mutation tests across client/contact/site/item/shared context,
  plus deletion attempts against frozen evidence and financial redaction tests.
- End-to-end flows for request conversion, optional review and withdrawal,
  revision, replacement send, acceptance/handoff, lost-family renewal, internal
  revision versus client request and legacy handoff repair.
- Widget/card/detail parity tests with scope filters, multiple actions per
  family, overdue/validity boundaries, missing dates, hold, archived history,
  new-work/change-order segmentation and datasets exceeding display/page caps.
- Historical/as-of fixtures proving a future draft/send/master edit cannot
  change earlier-period totals, client-renewal preserves old losses, compatibility
  records are not double-counted and unknown inputs remain visibly unknown.
- Browser checks at the documented widths/zoom and keyboard paths, with exact
  version navigation and conflict recovery. Run existing contract/API/web and
  release/upgrade checks; do not rely solely on mocked happy-path tests.
- Upgrade/restore evidence: original-column hashes, old event/snapshot JSON,
  document checksums/links, runtime grants, model constraints and sampled report
  reconciliation. During rollout monitor command conflicts/failures, duplicate
  family pointers, acceptance without project links, snapshot completeness and
  dashboard/analytics latency; none of those invariant failures is acceptable.

Completion means the worked fixture and failure/concurrency cases pass in the
UI, widgets and analytics, existing history remains readable, and the upgrade
can be restored. A schema migration or renamed status dropdown alone is not
completion.
