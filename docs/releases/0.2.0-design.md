## 2. High-Level Objectives

### 2.1 0.2 Themes

#### Theme A — Native Estimating and Quoting

Replace the external Excel-based estimating workflow with a native Pulse quote builder capable of performing the calculations, supplier-cost analysis, labor analysis, and proposal preparation required to produce a real client quote.

The implementation principle is:

> **Achieve functional parity with the current Excel estimating workflow first, then enhance it.**

#### Theme B — Lifecycle Workflow and User Clarity

Make each lifecycle phase intentional and visually obvious:

- **Request:** information gathering and qualification.
- **Quote:** solution design, estimating, review, proposal preparation, and client submission.
- **Project:** execution of approved work.
- **Change Order:** a quote originating from an approved project to modify scope and/or cost.
- **Billing:** conversion of completed work into invoicing and payment tracking.

0.2 focuses primarily on the Request → Quote → Proposal portion of the lifecycle while preserving clean handoffs to Project and Billing for later releases.

#### Theme C — Productization and Administration

Begin moving Pulse from an internally deployed application toward a distributable product by adding:

- In-application update awareness and controlled update execution.
- License/access-key validation foundations.
- Admin-managed visual palettes and design tokens.
- User feedback collection.
- Consistent permissions for new administrative capabilities.

### 2.2 Product Principles

- Pulse is a **lifecycle management platform**, not a collection of disconnected modules.
- Data moves forward through the lifecycle without losing historical context.
- Sent quote versions are historical records and must not silently change.
- Human estimators remain in control; automation should guide rather than replace judgment.
- 0.2 should capture clean structured data that can support future MCP/AI assistance.
- AI recommendation behavior is **not** a 0.2 requirement, but the data model should not block it.
- Avoid large manual catalog-modeling projects before they provide value.
- Security boundaries established in 0.1 must remain intact.
- Live master data may change, but historical commercial records must preserve the values that were actually used.

### 2.3 Success Metrics / Definition of Release Success

0.2 is successful when:

- A normal Pulse-mode quote can be created, estimated, reviewed, turned into a client-facing proposal, sent, locked, revised, and refreshed without using the legacy Excel worksheet.
- Reference Excel quote scenarios can be reproduced by the native calculation engine within agreed financial rounding tolerances.
- Every quote line can preserve the supplier/source cost used at the time of estimating.
- Changing an item or supplier price later does not modify historical sent quote values.
- Editing a Client, Contact, Site, Item, Supplier, or workspace setting does not rewrite historical sent quotes, generated proposals, projects, or issued invoices.
- Internal quote review has an auditable reviewer, decision, timestamp, and change-request history.
- Sent quotes automatically expose when their validity window has passed and show **Needs Refresh** without confusing that condition with the quote's business status.
- Request/Quote phase deadlines and sales follow-up dates are no longer represented as one ambiguous "due date."
- Users can identify Request, Quote, Project, and Billing records immediately from a consistent record header and lifecycle visual language.
- Admins can manage reusable application palettes without hard-coded per-screen colors.
- An administrator can see the installed Pulse version and whether an update is available.
- An update can be initiated through Pulse without exposing unrestricted Docker control to the web or API container.
- License validation can tolerate temporary loss of internet connectivity and never destroys or corrupts customer data.
- 0.1.1 historical data and LEGACY quote records remain supported.

### 2.4 Scope Boundaries

#### In Scope for 0.2

- Native quote-building workflow.
- Supplier profiles and supplier-to-item relationships.
- Supplier pricing and price history/source tracking.
- Estimating/calculation engine expansion.
- Quote item and solution-building enhancements.
- Quote review workflow.
- In-app notification foundation.
- Quote deadline and validity redesign.
- Quote revisions and sent-version locking refinements.
- Proposal/template builder and PDF generation.
- Lifecycle page visual consistency.
- Admin-managed theme/palette system.
- Point-of-contact profile improvements.
- Update-check and controlled self-update architecture.
- License/access-key validation foundation.
- User feedback page.
- Lifecycle document classification, tagging, filtering, and cross-lifecycle file discovery.
- Explicit snapshot-vs-live data ownership rules across the lifecycle.
- Feature flags and staged rollout controls for major 0.2 capabilities.
- Document revision/version control for drawings, specifications, supplier quotes, proposals, and other lifecycle files where version history matters.

#### Architecture-Aware but Not Full 0.2 Implementations

- Full Project execution management.
- Full Change Order management beyond preserving the quote-from-project relationship.
- Full Billing/accounting workflow.
- AI/MCP-assisted quoting.
- Automatic AI detection of commonly related items.
- Advanced procurement.
- Full native mobile applications.

#### Stretch / Future-Ready

- **Progressive Web App (PWA):** install Pulse from iOS/Android/browser and launch in standalone full-screen mode. The web architecture should remain compatible with this, but PWA delivery is not a release blocker unless promoted into scope later.

## 3. Architecture & Data Model Changes

### 3.1 Current Architecture to Preserve

Pulse 0.1.1 already has the desired primary ownership boundary:

```text
Browser
  ↓ HTTPS
Caddy
  ↓
Next.js Web
  ↓ /api
NestJS API
  ├─ PostgreSQL / Prisma
  ├─ MinIO
  └─ ClamAV
```

0.2 should preserve these rules:

- Next.js owns presentation and browser state.
- NestJS owns authoritative business rules, validation, authorization, transactions, calculations, integrations, and snapshot creation.
- Prisma/PostgreSQL remain the authoritative relational data layer.
- Generated proposals/documents continue to use the lifecycle document/storage architecture.
- Shared request/response contracts remain in `packages/contracts`.
- The web application must not gain direct database access.
- The web/API containers must **not** receive unrestricted Docker socket access for the updater.
- Historical records must be rendered from stored snapshots rather than reconstructed from today's master records.

### 3.3 Snapshot vs. Live Data Ownership

Pulse 0.2 must explicitly define which data remains linked to the current master record and which data becomes an immutable historical snapshot as information moves through the lifecycle.

The guiding rule is:

> **Operational relationships may stay live while a record is being worked, but any data that explains what was priced, reviewed, sent, accepted, issued, or executed must be preserved historically.**

This prevents later edits to a Client, Contact, Site, Supplier, Item, workspace setting, or template from silently rewriting the historical meaning of an existing quote, proposal, project, or invoice.

#### Ownership Categories

Every lifecycle field should be treated as one of three categories.

**Live Reference**
- Points to the current authoritative entity.
- Used for navigation and current operational context.
- Appropriate for current assignee, collaborator, client relationship, contact relationship, site relationship, supplier relationship, and catalog relationships.
- Example: a Quote retains `clientId` so a user can open the current Client profile.

**Historical Snapshot**
- Stores the value actually used at a meaningful lifecycle event.
- Does not change when the source entity later changes.
- Example: the client name, contact details, supplier price, scope, and line descriptions shown on a sent quote.

**Derived / Computed State**
- Recalculated from authoritative inputs while a record is editable.
- Once the record reaches the relevant lock/version event, the resulting value is preserved in the historical snapshot.
- Example: quote total, tax, gross margin, financial summary, and `validUntil`.

#### Client / Contact / Site

While a Request or Draft Quote is being prepared, Pulse may use current directory data from the linked Client, Point of Contact, and Site.

At the point a Quote revision is sent, Pulse must preserve the presentation data used by that revision, including:

- Client display/legal name as presented.
- Contact name.
- Contact email.
- Contact work/main phone and mobile where used.
- Site name.
- Site address.
- Relevant proposal/billing identity fields used in the generated proposal.

If any of those directory records are changed afterward, the historical Quote and Proposal remain unchanged.

The live entity IDs remain so the user can still navigate from the historical record to the current Client, Contact, or Site.

#### Items

The Item catalog is live reference data.

A QuoteItem is a commercial snapshot.

It must preserve the item information actually used in that Quote revision, including:

- Name.
- Description.
- Manufacturer/brand.
- SKU.
- Part number.
- Quantity.
- Unit of measure.
- Unit cost.
- Unit sell price.
- Markup.
- Discount.
- Taxable state.
- Image/product reference where required.
- Applied labor relationship or labor quantity where applicable.

Changing the Item catalog later must not alter previous QuoteItems.

#### Supplier / Pricing

Supplier and SupplierItem records represent current sourcing information.

Once a supplier price is used for estimating, the QuoteItem must preserve enough information to explain that cost later:

- Supplier identity/name.
- Supplier SKU/reference.
- Supplier unit cost used.
- Currency.
- Effective or verification date.
- Price valid-until date when known.
- Supplier quote/reference document or URL.
- Manual override/provenance information where applicable.

Future supplier price changes affect future estimates and explicit revisions only.

They do not rewrite previously sent Quote revisions.

#### Quote

A Draft Quote may use current master/reference data and recompute derived financials.

A sent Quote revision becomes immutable historical evidence of the offer made to the client.

The sent revision must preserve:

- Quote number.
- Revision number.
- Client/contact/site presentation data.
- Scope.
- Quote line snapshots.
- Supplier-source snapshots.
- Financial totals.
- Tax result.
- Proposal notes.
- Proposal template version.
- `sentAt`.
- `validUntil`.
- Internal review outcome applicable to the sent content.
- Generated proposal reference.

Changes to the commercial content after sending should normally require a new revision.

An admin-only correction mechanism may exist for exceptional mistakes, but it must be audited and must never silently rewrite history.

#### Proposal

A generated proposal is always a historical artifact once generated, and especially once sent.

It must remain bound to:

- Quote ID.
- Quote revision.
- Proposal template/version.
- Generated file/document ID.
- Generation timestamp.
- Generating user.
- File checksum/hash.

Later edits to the proposal template must not modify previously generated proposals.

#### Project

When a Quote becomes a Project, the Project must preserve the approved commercial baseline.

The Project may retain live references to the current Client, Contact, and Site for ongoing operations.

However, later edits to those master records—or later Quote revisions—must not silently rewrite the approved baseline of an already-created Project.

At minimum, preserve:

- Source Quote ID.
- Source Quote number.
- Source revision.
- Source calculation mode.
- Quote financial snapshot.
- Approved scope/baseline needed for execution.
- Relevant Proposal/document references.

Changes to approved scope after Project creation should occur through an explicit Change Order or another deliberate synchronization workflow.

#### Invoice / Billing

An issued Invoice must preserve the values that were true when the invoice was issued.

That includes:

- Billing identity.
- Project/reference numbers.
- Amounts.
- Tax results.
- Payment terms used.
- Relevant contact/address presentation data.

Later Client, Project, tax, or workspace-setting changes must not rewrite an issued invoice.

#### Documents

The stored file content should be immutable once uploaded unless Pulse explicitly creates a new version/replacement record.

Editable document metadata may include:

- Document type/category.
- Tags.
- Description.
- Classification/relationship metadata.

Replacing a drawing, specification, RFP, supplier quote, or similar file with a newer version should create traceable version history rather than silently replacing the historical binary.

#### Workspace Settings / Themes

Pure UI and operational settings remain live, for example:

- Color palette.
- Theme.
- Locale.
- Display preferences.

Commercially meaningful settings must be captured when they affect a transaction.

Examples include:

- Tax rule/result used in a Quote.
- Currency.
- Quote validity rule used to produce `validUntil`.
- Proposal template version.

Changing those settings later must not recalculate historical records.

#### Snapshot Transition Points

Snapshot creation must be deterministic and server-controlled.

Expected transition points include:

1. Request → Quote creation:
   - initialize Quote context snapshot from Request/Client/Contact/Site.

2. Quote item insertion:
   - copy relevant Item and Supplier information into editable QuoteItem state.

3. Submit for Review:
   - bind review to an exact Quote content version.

4. Proposal Generation:
   - bind output to exact Quote revision and Template version.

5. Quote Send:
   - freeze the commercial snapshot used for that sent revision.

6. Quote Revision:
   - preserve prior revision; create new editable state; optionally refresh live pricing/reference data.

7. Quote → Project conversion:
   - snapshot approved Quote financial/scope baseline into Project.

8. Invoice issuance:
   - freeze billing identity and financial values applicable at issuance.

#### Backend Enforcement

Snapshot behavior belongs in NestJS domain services, not React.

Implementation requirements:

- Create explicit snapshot-builder/domain functions.
- Never dynamically render historical commercial records solely from current Client/Item/Supplier data.
- Reject writes to immutable snapshot fields after their lock transition.
- Make revision/version creation additive rather than destructive.
- Audit permitted administrative corrections.
- Include snapshot expectations in shared contracts and service tests.
- Use transactions for transitions that create both a new lifecycle state and its historical snapshot.

#### Migration / Compatibility

The current Quote model already contains several snapshot fields for request, contact, site, scope, and internal notes, while QuoteItem and QuoteRevision already behave as historical records.

0.2 should formalize and extend that architecture rather than introducing a parallel snapshot system.

Migration rules:

- Preserve all existing snapshot values.
- Backfill only when the source and historical value can be identified confidently.
- Never overwrite an existing historical snapshot with today's master data.
- Do not guess when historical meaning is ambiguous.
- Mark ambiguous records for stewardship or retain the existing value.
- Maintain LEGACY Quote compatibility.

### 3.4 Feature Flags and Staged Rollout Architecture

Pulse 0.2 is large enough that deployment and feature activation should be separate concerns.

The application should support centrally managed feature flags so a capability can exist in the deployed build while remaining disabled or limited to selected users/workspaces until validated.

Recommended flag scopes:

- Global/system-wide.
- Workspace-wide.
- Role-based or permission-based.
- Explicit user allowlist for internal testing.

Initial flags may include:

- Native Pulse estimating.
- Supplier management.
- Quote review workflow.
- Proposal template builder.
- New lifecycle file/document experience.
- Theme palette editor.
- Self-update UI.
- License enforcement.
- PWA installability if included.

Recommended rollout states:

- `OFF`
- `INTERNAL`
- `PILOT`
- `ON`

Implementation rules:

- Flags must be evaluated server-side for authoritative backend capabilities.
- Frontend checks are presentation only and must not be the security boundary.
- Disabling a flag must not delete or corrupt data created while it was enabled.
- Database migrations must remain safe even when the corresponding UI feature is disabled.
- Flags should default conservatively during upgrade.
- Changes to system-level rollout flags should be admin-only and audited.
- Avoid long-term permanent branching in code; flags are rollout controls, not substitutes for deleting obsolete behavior after stabilization.

A lightweight database-backed configuration is sufficient for 0.2; a third-party feature-flag service is not required.

### 3.6 Proposed Database Schema Updates

Exact names may change during implementation planning, but the domain relationships should remain.

#### Feature Flags

Recommended `FeatureFlag` model:

- `id`
- `key`
- `description`
- `state`
- `enabled`
- optional workspace scope
- optional role/user targeting configuration
- `createdAt`
- `updatedAt`
- `updatedById`

A separate targeting table may be introduced if role/user/workspace targeting becomes complex.

Flag values should use stable keys in shared contracts rather than arbitrary free-form strings scattered through the codebase.

#### Lifecycle Document Classification and Tags

Extend the existing `LifecycleDocument` model rather than replacing it.

The current model already provides lifecycle ownership, `category`, `tags`, storage metadata, scanning state, uploader, and timestamps. 0.2 should formalize those fields into a consistent classification system.

Recommended changes:

- Replace ad-hoc category usage with a controlled `DocumentType`/document-category vocabulary while preserving a migration path for existing category strings.
- Keep free-form/reusable tags for secondary classification.
- Add indexes/search support needed for filtering by document type, tag, lifecycle record, client, supplier context, and date.
- Add optional supplier relationship metadata where useful, or derive supplier context through the related Quote/Supplier pricing record rather than duplicating ownership.
- Preserve the existing `LifecycleDocument` links to Request, Quote, Project, and Invoice.
- Do not duplicate the physical file merely to make it visible from a Client or another lifecycle view; use relationships and lifecycle context to discover the same document.

Initial controlled document types should include:

- Architectural Drawing / Drawing
- RFP / RFQ
- Client Email / Correspondence
- Site Photo
- Supplier Quote / Supplier Pricing
- Client Proposal / Quote PDF
- Purchase Order
- Contract / Agreement
- Datasheet / Product Documentation
- Scope / Specification
- Other

#### Document Revision / Version Control

For document classes where revision history matters, Pulse should preserve a traceable version chain instead of treating every upload as an unrelated file or overwriting the prior binary.

Recommended additions to `LifecycleDocument` or a companion versioning model:

- `documentFamilyId` or `supersedesDocumentId`
- `revisionLabel` such as `Rev A`, `Rev B`, `1`, `2`, or supplier-provided revision
- `versionNumber` as an internal monotonically increasing integer
- `issuedAt`
- `supersededAt`
- `isCurrentVersion`
- optional `revisionNotes`
- optional `sourceRevision`
- uploaded/issued-by metadata

Recommended behavior:

- Uploading a replacement drawing/specification can create a new version in the same document family.
- The prior version remains accessible and immutable.
- Only one version in a document family is treated as the current version.
- Search results should prefer the current version while allowing users to open revision history.
- Supplier quotes can retain multiple revisions so estimators can see which supplier document supported a particular price snapshot.
- Generated client proposals should already be immutable and should not be overwritten; a newly generated proposal becomes a new historical document/version.
- Deleting a current version should not silently promote an older version without an explicit controlled action.
- Version relationships must not require copying the same binary when the document itself has not changed.

The first 0.2 implementation should prioritize revision control for:

- Architectural drawings.
- Scope/specification documents.
- RFP/RFQ documents.
- Supplier quotes/pricing sheets.
- Generated client proposals where multiple generations/revisions exist.

Recommended tagging behavior:

- A document has one primary type/category.
- A document can have multiple secondary tags.
- Tags can describe trade, location, phase, vendor, discipline, or other useful context.
- Tags should be normalized case-insensitively.
- Existing `tags String[]` can remain for the initial implementation if normalized/searchable behavior is sufficient; a dedicated many-to-many tag model should only be introduced if governance, aliases, descriptions, permissions, or analytics later require it.

## 4. Implementation Breakdowns — Core Development Work

### 4.1 Feature: Quote Lifecycle, Status, Deadline, and Revision Model

#### Requirement

Fix the ambiguity between quote status, quote creation deadline, sales follow-up date, quote sent date, quote pricing validity, and true lifecycle expiration.

#### Target Behavior

A quote can simultaneously be:

- **Business Status:** Sent
- **Validity:** Needs Refresh
- **Follow-Up:** Due tomorrow

Those are separate concepts.

#### Recommended Status Model

Suggested business states:

- Draft
- Review
- Changes Requested
- Ready to Send
- On Hold
- Sent
- Accepted
- Rejected
- Expired
- Cancelled

Notes:

- Internal reviewer **approval** is a review decision, not the same thing as client acceptance.
- Consider renaming client-facing `Approved` to `Accepted`.
- `Expired` means the opportunity/quote was no longer viable before successful submission/acceptance.
- Missing a deadline first produces an **Overdue** computed flag.
- A sent quote beyond its validity becomes **Needs Refresh** while retaining its business state.

#### Backend Tasks

- Define explicit shared enums/contracts.
- Implement derived deadline state.
- Implement derived quote validity.
- Calculate/store `validUntil` when sent.
- Default business rule: 30 days unless future configuration overrides it.
- Preserve sent-version locking.
- Keep admin-only un-send as an audited exception.
- Revision creation preserves prior sent snapshot and creates new editable revision.
- Refresh live supplier pricing only into the new revision.

#### Frontend Tasks

- Replace ambiguous Due Date labels.
- Show status, draft deadline, next action, and validity separately.
- Show Needs Refresh banner/action.
- Add Create Revision and Refresh Pricing.
- Add audited admin correction/un-send UI.

## 12. Release Summary

Pulse 0.1 established the lifecycle and production foundation.

Pulse 0.2 should make the **Quote** phase genuinely operational.

The release adds:

- structured sourcing,
- supplier-backed pricing,
- deterministic calculations,
- explicit snapshot-versus-live ownership,
- review controls,
- lifecycle-aware deadlines,
- revisions and historical integrity,
- proposal publishing,
- lifecycle document classification/tagging/cross-record discovery and revision control,
- notifications,
- clearer UX,
- customizable theming,
- product updates,
- licensing foundations,
- and feedback collection.

The intended outcome is that a team can take a qualified Request, design and price the solution inside Pulse, review it, publish a professional Proposal, send it, preserve exactly what was sent, revise it when required, and carry that stable approved history into later Project and Billing releases without current master-data changes rewriting the past.
