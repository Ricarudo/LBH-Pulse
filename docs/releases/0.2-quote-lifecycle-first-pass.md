# Quote lifecycle — first implementation pass

Date: 2026-09-25. See the [implementation plan](0.2-quote-lifecycle-implementation-plan.md) for the complete target behavior.
Subsequent work is recorded in the [second-pass report](0.2-quote-lifecycle-second-pass.md).

## Implemented behavior

- Ordinary quote updates reject commercial changes when the quote is sent or closed. Protected fields include title, client/contact/site links, preparation deadline, shared scope details, trades, proposal notes and pricing. Owner, collaborators and operational activity remain available through their existing paths.
- Commercial PATCH and proposal-note writes acquire the same parent-row lock used by send and financial writes. PATCH rechecks state after acquiring the lock and returns a conflict if its earlier validation used an older row. Archiving while a writer waits also prevents that write.
- New send/revision evidence includes schema version, title, client name, site and scope details alongside existing contact, context and exact financial snapshots. This does not invent missing evidence for old sends.
- Quote list and detail selectors group Working, Awaiting response and Closed outcomes. The UI calls the existing `Approved` outcome **Accepted**, including the project handoff action. Wire/storage values remain compatible with the current API.
- Quote list filters can select a lifecycle group. Selecting Closed from the saved Open view widens the view so results appear; the selection survives URL round trips. Searching “accepted” finds legacy `Approved` records.
- Detail, proposal and pricing editors reflect the commercial lock. Assignment/collaborator editing remains available.

## Shared foundations, not activated workflows

`packages/contracts/src/quote-lifecycle.ts` defines publication/outcome vocabulary, legacy presentation adapters, inclusive business-date validity, the default 30-calendar-day validity calculation, and family-aware pipeline/win-rate helpers.

The pipeline helper chooses the current sent offer while a replacement draft exists. The fixture demonstrates an outstanding offer of 1,000 and replacement draft of 1,200: pipeline stays 1,000 until the replacement is sent, becomes 1,200 after that send, and disappears from open pipeline when accepted. It rejects invalid or duplicate selected identities. The win-rate helper counts accepted / (accepted + rejected + expired), excludes cancellations/open families, and rejects duplicate family IDs.

These helpers are **not yet used by live analytics or Home widgets**. Existing Decimal financial calculations and event-quality handling remain in place. No family identity change is activated in this pass.

## Database candidate

`apps/api/prisma/migration-plans/quote-lifecycle-foundation.sql` contains a tested candidate for:

- `QuoteFamily` and a `QuoteVersion` sidecar referencing each exact Quote ID;
- same-family current/predecessor pointers and unique revision numbers;
- at most one open draft, outstanding offer and accepted version per family;
- immutable, schema-versioned content snapshots bound to the exact quote/content version;
- content-bound review submissions, one pending review, and no self-review;
- operation retry-key uniqueness and stored request hashes/results;
- separate preparation, follow-up and pricing-validity dates.

The sidecar is a provisional implementation adjustment to the plan's new Quote columns: it isolates additive metadata while preserving existing Quote rows and protected imported values. It does **not** authorize reusing a Quote ID for a new revision in the future model. Each future revision still needs a new Quote row plus its own version metadata.

This SQL is deliberately outside `prisma/migrations`. The active Prisma schema/client, seven-migration deployment sequence and 0.1.2 release manifest remain unchanged. The release tests require exact agreement between active migration directories and release metadata; promoting this SQL alone would violate that contract and leave readers unaware of families.

The candidate is not production-ready: application transitions must validate pointer publication/outcome consistency, enforce send/review/validity rules, freeze commercial storage, emit events and implement retry behavior. Backfill, indexes based on actual query plans, role grants and Prisma integration still require the coordinated 0.2 cutover. The snapshot trigger prevents ordinary row update/delete, not privileged DDL or database-owner actions.

2. Implement new-row revisions, atomic replacement send/supersession, renewal into a new family, and acceptance linked atomically to the exact project/financial snapshot. Retire legacy undo-send and in-place reopening at activation.

Count families for opportunities and outcomes, exact versions for send/revision activity, and accepted financial snapshots for handoff/margin. Run the plan's cross-surface scenarios before enabling the new writer.
