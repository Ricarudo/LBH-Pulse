# Calculator and database integration reference — Pulse 0.2

Reviewed 2026-10-30 against the current working tree, including uncommitted Quote Builder work. This document is a reference and proposed integration contract, not a migration or a claim that all described features are deployed.

## 1. Most important distinction

The calculator already has database persistence code for **editable working inputs**. It does not yet publish its results into the authoritative Quote financial model.

Today, the existing Quote financial normalizer reads either LEGACY summary fields or PULSE QuoteItem rows. It does not read QuoteBuilderWorkspace. Sending, accepted-project budgets, financial snapshots, and downstream reports still depend on that existing financial path.

Consequently, a Builder displaying a calculated amount does not establish that the same amount will appear in Quote lists, a sent snapshot, a project, or analytics. Do not treat successful autosave or server calculation verification as financial publication.

Status vocabulary in this reference:

- **Existing:** implemented in the established application code; deployment is a separate question.
- **Working tree:** calculator implementation present locally, including an unapplied/unverified-here deployment migration. Do not assume a running installation has it.
- **Staged:** experimental quote-family service and SQL, not connected to the normal controllers.
- **0.2 target:** documented lifecycle requirement or broader release expectation.
- **Recommendation:** proposed integration design requiring implementation; names are illustrative unless identified as existing.

No database was inspected or changed for this document. The previous live inventory had seven migrations and 44 application tables. The current Prisma source has 46 models because the newer calculator work adds two. Whether its eighth migration has since been deployed was not checked here.

## 2. Architecture and ownership

```text
Catalog Items + company settings + labor classes
                    |
                    v
Editable Builder inputs <---- user overrides / explicit refresh
                    |
                    v
Pure calculateQuote(inputs, configuration)
                    |
                    v
Result + diagnostics + component breakdown
                    |
          [MISSING INTEGRATION]
       server-validated publication
                    |
                    v
Authoritative Quote financial summary and content identity
                    |
           review / send snapshot
                    |
         +----------+------------+
         v          v            v
     Proposal    Analytics   Accepted project
```

The calculator computes. The API checks authorization, loads configuration, validates document structure, coordinates writes and freezes evidence. PostgreSQL stores the records and enforces relationships/concurrency. The browser must not connect directly to PostgreSQL or decide that a quote is accepted merely because it calculated successfully.

Keep the pure engine independent of React, Prisma, lifecycle state, network, system clock and current Item lookups. Its reproducibility comes from receiving every necessary input explicitly. Existing engine entry point: `calculateQuote` in `packages/quote-calculator/src/index.ts`.

Do not build a second editable financial truth. A saved draft, a published draft calculation, and an immutable sent snapshot have different responsibilities, but must be linked by exact content identity.

### Proposed lifecycle storage and the consolidation recommendation

The staged SQL still adds QuoteFamily, QuoteVersion, QuoteContentSnapshot, QuoteReview and QuoteOperation. Our subsequent simplification recommendation is to move QuoteVersion's lifecycle fields onto Quote, leaving four new tables. That redesign has **not** been implemented or approved as a finished migration.

| Proposed table | Purpose |
| --- | --- |
| QuoteFamily | One opportunity across original quote and revisions; current draft/offer/accepted references, source links, final outcome and renewal provenance. |
| QuoteContentSnapshot | Immutable commercial evidence for exact reviewed/sent content, including calculation evidence after integration. |
| QuoteReview | Content-bound reviewer submissions/decisions, actor, timestamps and reason. |

## 4. What the working-tree calculator migration changes

`202610290001_quote_builder_workspace` is separate from the staged family SQL. It:

1. Adds WorkspaceSettings.quoteCalculationSettings JSON with company starting values.
2. Adds QuoteLaborClass, with hourlyRate DECIMAL(20,8) and enabled status.
3. Adds Item.defaultProductionRate DECIMAL(20,8), defaultCrewSize DECIMAL(12,3), and defaultLaborClassId with a foreign key/index.
4. Adds QuoteBuilderWorkspace with quoteId primary/foreign key, schemaVersion, JSON state, writeToken and timestamps.

It does not migrate legacy quotes into Builder lines, rewrite historical totals, add suppliers, or activate family revisions. Existing migrations should remain unchanged. Applying this migration is necessary before running the new Builder DB code, but is not sufficient for financial publication.

## 5. Current Builder API contract

All routes below are implemented in the working tree; availability on a deployed server depends on its code and migrations.

| Method/path | Permission | Request and result | Database effect |
| --- | --- | --- | --- |
| GET /api/quotes/:quoteId/builder | quotes:read | Returns state, writeToken, configuration, configurationId, calculation, unavailableItemIds | Read-only. Does not create an empty workspace row. |
| PUT /api/quotes/:quoteId/builder | quotes:write | `{state, expectedWriteToken}` → `{state, writeToken}` | Saves only Builder working state/token. |
| POST /api/quotes/:quoteId/builder/calculate | quotes:read | `{state, configurationId}` → `{calculation, configurationId}` | Recalculates supplied inputs on server; no financial publication or save. |
| GET /api/settings/quote-calculation | Any of quotes:read, items:read, settings:read | Returns full configuration including labor classes and configurationId | Read-only current settings. |
| PUT /api/settings/quote-calculation | settings:write | `{settings, expectedConfigurationId}` | Updates current settings after a configuration conflict check. |
| POST /api/settings/labor-classes | settings:write | `{name, hourlyRate, enabled}` | Creates a current labor class; returns configuration. |
| PATCH /api/settings/labor-classes/:id | settings:write | `{name, hourlyRate, enabled}` | Updates class; returns configuration. No expected-version token in this request today. |
| GET /api/items/search | items:read | Existing Item search query → `{items}` | Active Item selection. |
| GET /api/items/:id/detail | items:read | Item, statistics, price history and recent quote usage | Existing usage is based on existing financial records; Builder JSON usage must be integrated deliberately. |

Use the existing browser API wrapper (`apps/web/src/lib/api/client.ts`) and Builder client (`apps/web/src/lib/api/quoteBuilder.ts`). They send the session cookie and mutation headers X-Pulse-Request and X-Pulse-CSRF. Mutations also undergo origin checks. A separate calculator application on another origin needs a deliberate authentication/integration design; the existing endpoints are not an unauthenticated public calculation service.

Builder requests have an 8 MB limit; document validation allows up to 5,000 lines and 200 groups. This is a limit, not a demonstrated performance target.

### Save/concurrency behavior

- Before first save, writeToken is null. Send expectedWriteToken: null.
- First saved row receives token 1. Later saves send the last server-issued token; success increments it.
- Parent Quote locking serializes saves with host operations. Save rechecks the existing commercial lock and requires PULSE mode.
- An archived/missing Quote is unavailable. A frozen Quote rejects edits.
- A new Builder workspace cannot be created over a populated existing QuoteItem BOM. No automatic conversion exists.
- Structurally valid incomplete/invalid estimating inputs can be saved. Calculation readiness is separate from persistence success.
- An unknown document schemaVersion is rejected rather than silently interpreted.
- A newly selected Item must exist and be active. Previously saved unavailable Item references retain copied inputs and are reported on load.
- Save conflicts return HTTP 409 with BUILDER_WRITE_CONFLICT; configuration verification/settings conflicts use BUILDER_CONFIGURATION_CHANGED. Preserve local edits and offer an explicit reload/reconciliation path. Do not overwrite by automatically retrying with a newer token.
- A lost save response is ambiguous: a subsequent stale-token conflict may mean the first save succeeded. Load/compare before retrying; PUT currently has no command idempotency key.

### Three distinct identities

| Identity | Meaning | Not interchangeable with |
| --- | --- | --- |
| writeToken | Revision of editable Builder JSON | Quote revision number or approved content identity |
| configurationId | SHA-256 identifier of the current settings/class payload | A retrievable historical configuration record; currently none exists |
| Quote content version / snapshot ID — target | Exact commercial content reviewed, sent and accepted | Autosave sequence or family ID |

schemaVersion describes document format. An engine/calculation-policy version is also needed for reproducibility; it is not the same thing as schemaVersion and is not currently included in Builder save state.

## 6. Inputs: precise field meanings

The exact schemas/types live in `packages/contracts/src/quote-builder.ts`. Reuse them rather than defining a loosely similar interface.

### Workspace document

- `groups`: id, title, accent, order. Presentation only; grouping must not change price.
- `lines`: stable id, quantity, mode, material inputs, labor inputs, plus presentation/catalog metadata.
- `projectCosts`: travelTotal, equipmentRentalTotal, lodgingNightlyRate, lodgingHeadcountOverride.
- Line metadata: itemId or null, name, unit, proposalDescription, imageUrl, groupId or null, order, origins.
- origins records item/company/manual/bulk provenance for fields; it does not capture the original Item version, supplier evidence or full settings snapshot.

### Per-line financial inputs

| Field | Meaning |
| --- | --- |
| quantity | Decimal quantity, at most 3 decimal places. Zero lines contribute zero without requiring all labor inputs. |
| mode | MATERIAL_AND_LABOR, MATERIAL_ONLY or LABOR_ONLY. This is a line mode, distinct from Quote.calculationMode (PULSE/LEGACY). |
| material.baseUnitCost | Cost per selected quantity unit, copied from Item.cost or entered manually. |
| material.contingency | Fraction of base material cost. |
| material.freight | Fraction of base material cost. |
| material.margin | Target margin fraction, not markup percentage. |
| material.materialIvuEnabled | Whether the material IVU component applies under the engine's current policy. |
| material.materialIvuRate | Fraction used for that component. |
| labor.laborClassId | Class resolved from the explicitly supplied configuration. |
| labor.productionRate | Quantity units completed by the configured crew per ideal working hour. |
| labor.crewSize | Crew count used for direct hours and effective-crew calculation. |
| labor.overtimeMultiplier | Hourly-rate multiplier; 1 means no increase. |

**Production rate is not legacy defaultLaborHours.** The current Builder does not derive one from the other. A crew completing 10 units/hour is different from a worker spending 10 hours/unit. Unit and crew definitions must agree with the Item default.

Item defaults are copied, not live-bound. Current helper copies cost, description/image, production rate, crew, labor class and applicable company defaults. It does not price from Item.sellPrice or Item.markupPercent. New lines initially have zero quantity. PRODUCT defaults to Material + Labor; current helper maps both LABOR and SERVICE Items to Labor Only. SERVICE pricing beyond this behavior needs an explicit adapter decision.

Current Builder does not automatically expand Item kits/required labor through the old BOM engine. If that behavior is desired, create an explicit expansion adapter and then pass the resulting inputs to the calculator.

Indirect roles contain id, name, enabled, weeklyCost and allocationPercent (a fraction). Labor class rates have up to eight decimal places in their current database column. No labor-class costs should be invented to make a calculation complete.

These are current software defaults/formulas, not a determination of legal tax applicability. Keep policy identification and business approval separate from whether the code implements the formula.

### Numeric rules

- Builder inputs/results are decimal strings or null: `"125.50"`, `"0.115"`, null.
- null means missing/not configured, not zero. Empty-string form inputs should become null before serialization.
- All Builder rates are fractions: `"0.30"` = 30%. Existing markupPercent/discountPercent APIs use percentage points: 30 = 30%.
- Target margin formula is cost / (1 − margin); markup formula is cost × (1 + markup). They cannot share a field without conversion.
- Input schema permits up to 12 integer and 12 fractional digits for general decimal strings; quantity is restricted to 3 fractional digits. Database column capacities differ.
- Negative draft inputs may be persisted if structurally valid, but the calculator reports invalid rather than publishing them as prices.
- Zero denominator produces unavailable/null for relevant ratios. Do not coerce it to zero or Infinity.
- Match results to inputs by stable line ID; engine results are evaluated in stable identifier order, not UI order.

## 7. Current calculation sequence

This section documents the working-tree implementation, not a new formula specification.

1. **Direct labor:** installation hours = quantity / productionRate; direct hours = installation hours × crewSize; direct cost = direct hours × class hourly rate × overtimeMultiplier.
2. **Duration:** effective crew is the arithmetic mean of contributing crew sizes. Ideal hours = summed direct hours / effective crew. Practical hours = ideal hours × practicalTimelineFactor; days = hours / 8; weeks = hours / 40. This is the current parallel-work model, not a scheduled completion date.
3. **Indirect/payroll:** supervision = sum(weeks × enabled role weeklyCost × allocationPercent). Payroll burden applies to direct cost + supervision. Labor contingency applies after burden.
4. **Labor margin:** add duration-based vehicle cost and total equipment rental to payroll subtotal; divide by 1 − laborMargin.
5. **Other loaded amounts:** add annualRent / 52 × weeks; annualBondInsurance / 52 × weeks; lodging; total travel; and Fondo = post-margin labor amount × fondo.
6. **Allocation:** loaded labor / direct labor cost gives the allocation factor. Allocate to lines in proportion to direct cost, derive unit selling values, round each customer labor unit upward to cents, then extend by quantity.
7. **Materials:** raw unit = base + base×contingency + base×freight + applicable base×IVU + material profit. Profit = base/(1−margin) − base. Freight and IVU do not receive that margin. Round customer unit upward to cents, then extend by quantity.
8. **B2B component:** base = rounded customer labor extensions + raw material profit + raw material contingency. Multiply by b2bServiceTaxRate. Embedded material IVU is already in material selling values; do not add it again.
9. **Payable:** sum customer material extensions, customer labor extensions and B2B amount; round final payable to cents using half-up. Preserve the final rounding adjustment.

The engine uses an isolated decimal context with precision 40. Fractional extensions and tax can retain more than two places even though customer unit prices are cents.

Lodging defaults: headcount = ceiling(effective crew), nights = ceiling(practical days); headcount may be overridden. A positive lodging rate with unusable duration stays incomplete. If there is no direct labor cost allocation base, project costs must not disappear: the engine exposes entered, known, allocated and unallocated cost amounts and may leave the overall quote incomplete.

## 8. Outputs and the missing financial adapter

CalculationResult contains:

- status: complete / incomplete / invalid, plus diagnostic code/category/path/lineId/message;
- line material/labor direct and selling values, raw/customer units, extensions and rounding differences;
- material aggregate base cost, contingency, freight, embedded IVU, profit and customer selling value;
- labor analysis: effort, duration, supervision, burden, contingency, vehicles, equipment, margin-stage values, rent, insurance, lodging, travel, Fondo and allocation;
- entered/allocated/unallocated project cost analysis;
- tax component amounts/base/rate;
- rawFinalCustomerTotal, finalPayableTotal and payableRoundingAdjustment.

**It does not currently provide the full normalized QuoteFinancialSummary consumed elsewhere.** The existing summary includes materialRevenue, laborRevenue, serviceRevenue, preTaxContractValue, taxAmount, finalCustomerTotal, materialCost, laborCost, serviceCost, totalEstimatedCost, grossProfit, grossMarginPercent, markupPercent and estimatedDurationBusinessDays.

| Existing financial field | Required Builder integration decision |
| --- | --- |
| finalCustomerTotal | Use the verified final payable, while preserving raw value and rounding adjustment. Updating this alone is insufficient. |
| materialRevenue | Define treatment of embedded IVU and rounding. Do not blindly label a tax-inclusive component pre-tax revenue. |
| laborRevenue | Map allocated rounded customer labor values; keep component cost/margin distinction. |
| serviceRevenue | No distinct service result bucket exists today. Define mapping for SERVICE Items/custom services. |
| taxAmount | Explicitly classify embedded IVU versus added B2B and the sales-tax exclusion used by reports. Avoid duplication. |
| preTaxContractValue | Must reconcile with the agreed tax classification and payable total; source of pipeline and project budget. |
| materialCost | Define inclusion of freight, embedded purchase taxes and contingency as estimated cost versus allowance. Preserve all components. |
| laborCost | Must include the agreed loaded cost basis, not just directCost and not loadedTotal (which includes selling margin). |
| totalEstimatedCost / grossProfit | Derive from an explicit cost policy, with no double counting of equipment/travel/lodging. |
| grossMarginPercent | (preTaxContractValue − totalEstimatedCost) / preTaxContractValue × 100; null if denominator zero. Target labor/material margin is not overall realized estimated margin. |
| markupPercent | Gross profit / totalEstimatedCost × 100; null if denominator zero. |
| estimatedDurationBusinessDays | Existing field is integer-or-null; Builder practicalDays can be fractional. Define an explicit projection while retaining precise duration. Do not set a due date automatically. |

The classification decisions above are unresolved integration requirements. The current calculator arithmetic may be correct while the downstream accounting/reporting interpretation is still wrong.

Existing Quote.total is a final-customer-total compatibility field, not the sole authoritative input. Existing quote response generation recalculates from LEGACY fields or QuoteItems. Writing only Quote.total will not connect the calculator reliably.

Existing PULSE BOM rounds line subtotal/tax to cents and uses two-decimal QuoteItem money columns. Its ordinary line calculation defaults omitted lineTax to zero. Do not pass Builder results through it and assume identical tax/rounding behavior.

## 9. Recommended publication contract — not implemented

Introduce one explicit server operation to apply a completed estimate to the editable Quote. An illustrative name is `publishDraftCalculation`; this is **not an available API route**.

The request should identify quoteId, expected Builder writeToken, expected Quote commercial content version, configuration identity, engine/policy version and an idempotency key. Prefer calculating from the server-saved document; if accepting state in the same operation, save and publish atomically under the same concurrency checks. Do not accept a browser total as authoritative.

In one coordinated transaction/protocol:

1. Authorize quotes:write; lock in the agreed family → Quote order when families are active.
2. Recheck draft/editability and exact working inputs/configuration/content identity.
3. Calculate on the server with the same engine version; reject incomplete/invalid output and unresolved recovery costs under the agreed policy.
4. Build the normalized financial summary using the explicit component/tax mapping.
5. Store exact calculation evidence and source identity; update canonical draft financial fields/projection.
6. Increment the Quote commercial content version and invalidate old readiness/review/artifact references.
7. Record the business-level value change and operation outcome transactionally. Do not record every keystroke as a lifecycle transition.
8. Return the authoritative summary and all updated tokens/identities.

Decide whether to project Builder lines into an extended QuoteItem model or add a versioned Builder financial adapter directly into the canonical quote reader. Avoid round-tripping precise results through the current two-decimal columns. In either design, there must be one financial source selected for a given Quote, not two editors independently updating its value.

A quote with unpublished Builder edits must not be sent using an older published estimate. The UI should show a clear pending-calculation state, and the server send operation must enforce matching identities. An alternative is atomic calculate-and-send; it still needs the same validation/evidence boundary.

Important present gap: current mark-sent reads the existing Quote financial path and does not inspect Builder writeToken, diagnostics or configuration. Merely hiding its button in the Builder is insufficient protection.

## 10. Configuration persistence and historical reproducibility

Current session behavior is intentional but incomplete for historical evidence:

- Load obtains current settings/classes and a configuration hash.
- Saves return state/token without refreshing the session's rates.
- Explicit reload obtains current configuration and recalculates saved state.
- Line-copied material defaults/overrides remain in state, but labor class hourly rates and global labor settings are resolved from the newly loaded configuration.
- Calculate verification rejects an outdated configurationId; it cannot retrieve the old configuration from that ID.

For 0.2, published/reviewed/sent calculation evidence should preserve:

- document schemaVersion and calculator engine/policy version;
- exact inputs, selected source IDs and copied commercial facts;
- full effective settings and referenced labor class names/rates, not only their hash;
- exact result and normalized Quote financial summary;
- cost/tax classification, currency and rounding rules;
- operation, Quote content and snapshot identities;
- actor and effective timestamp;
- exact selected source/proposal document references when applicable.

This can be part of the existing proposed commercial snapshot payload. It does not automatically require a separate settings-history or calculation-history table. A future feature to reopen a draft with its original settings may also require persisting its configuration selection; current working-state JSON alone cannot do that.

## 11. Quote lifecycle integration expected for 0.2

| Action | Expected data behavior | Calculator behavior |
| --- | --- | --- |
| Create/edit draft | New Quote identity; editable working estimate | Save incomplete work; surface diagnostics. |
| Request review | Bind review to exact commercial content/snapshot | Supply complete reproducible calculation evidence. |
| Edit after review | Advance content identity; invalidate readiness/approval | Recalculate; do not reuse old approval. |
| Send | Freeze commercial identity, scope, selected documents, inputs/configuration/results and validity | Display frozen values; do not reprice from current settings. |
| Create revision | New Quote ID and new line IDs in same family, copied from frozen evidence | Copy inputs and original values; reset review/send/validity; refresh source prices only explicitly. Builder JSON is not currently copied by the staged family service. |
| Send replacement | Supersede previous offer only now | The draft did not replace the outstanding offer's pipeline value. |
| Accept | Accept current valid sent offer and create/link project in one transaction | Exact accepted financial snapshot becomes project baseline/change order. |
| Reject/cancel/expire | Close with explicit outcome and history | No recalculation or loss of frozen evidence. |
| Renew closed work | New linked family, preserving old decision | Copy to a new estimate, never reopen the old outcome. |

Publication is Draft or Sent. Family outcomes are Accepted/Rejected/Cancelled/Expired. Review, readiness and hold are distinct concepts. Default offer validity is 30 workspace-local calendar days; passing validity marks Needs Refresh, not automatic loss/closure.

The currently routed revision endpoint still implements the old in-place model. The staged family service is not a production-ready substitute: it needs coordinated readers, histories, commands and UI. Do not use the old revision endpoint and expect a new Quote ID today.

## 12. Analytics, widgets, projects and billing

The calculator supplies financial facts; it does not count business outcomes.

| Consumer | Expected basis |
| --- | --- |
| Quote list / client work / Home | One row/count per family. Offer and draft values shown separately when both exist. |
| Open pipeline | One pre-tax amount per open family: current sent offer first, otherwise active published draft estimate. Never add original and revision. Define how unpublished drafts appear without pretending they have authoritative value. |
| Historical pipeline | Snapshot/event facts known at the period end, not today's Item costs/settings or latest revision. |
| Win rate | Accepted / (Accepted + Rejected + Expired), once per eligible family decision. Cancelled/superseded/discarded are excluded. |
| Accepted value | Exact accepted pre-tax contract value, once per family. It is not invoiced revenue or cash received. |
| Accepted estimated margin | (sum accepted pre-tax value − sum accepted estimated cost) / sum accepted pre-tax value. Weighted by value, not averaged percentages. |
| Offers sent | Distinct sent version identities; retries do not add another send. |
| Project budget | Accepted original plus accepted change orders; no draft/superseded amounts. |
| Project actuals | ProjectExpense and delivery facts, separate from estimate. |
| Invoice / billing | Explicit billing operations and invoice amounts. Do not automatically post an invoice from calculator save. |
| Catalog usage | Ensure published Builder usage is represented in Item statistics, without counting every autosave or abandoned revision as a separate sale. |

Required reconciliation example, all values pre-tax: send 1,000 → create revision draft 1,200 → send revision → accept. Pipeline must be 1,000 → 1,000 → 1,200 → 0. This is one family, one revision, two sent versions, one accepted contract/project baseline of 1,200. With accepted cost 700, accepted estimated margin is 41.67%. A later accepted 200 change order raises project budget to 1,400 without another project.

Existing Home/current summaries and historical analytics must consume the same normalized financial definitions. Adding Builder values to only the Quote screen does not satisfy integration.

## 13. Broader 0.2 dependencies

These are release expectations, not currently available calculator API contracts:

- **Suppliers:** supplier identity, supplier-to-item offers, immutable price observations, source references, currency, effective/verified/valid-until dates, lead time and minimum quantity. Quote inputs need the exact selected cost and evidence. Include purchasing unit/pack conversion so box cost cannot be mistaken for unit cost. Current Builder schema has no supplier fields.
- **Currency:** current Builder inputs/results have no explicit currency field. Establish a single quote currency; reject unsupported mixed currencies or define and snapshot FX conversion before accepting them.
- **Documents:** existing LifecycleDocument/MinIO should provide exact source-file references. Formal document versions and referenced-file retention need implementation. Revisions reuse file references rather than duplicating binaries.
- **Proposals:** templates/template versions and generated artifacts must consume the exact calculated presentation/snapshot. A PDF renderer must not independently rerun pricing with newer defaults. The current builderPresentation helper prepares a view but is not a generated-proposal persistence system.
- **Internal financial permissions:** the release design discusses internal-cost restrictions; current Builder read endpoints use broad quote/item/settings read permissions and return configuration/calculation details. Fine-grained cost redaction must be implemented before promising restricted customer-facing or sales-only access.
- **Rollout/notifications:** feature flags and review notifications are broader work. They must not change historical reads or calculator arithmetic.
- **Themes, feedback, licensing and updater:** separate release domains. Do not embed them in calculation inputs or introduce tables merely to support this integration.

The original release design contains older open questions. For quote lifecycle semantics, the later quote-lifecycle implementation plan records the confirmed decisions and takes precedence in this workstream. Full workbook parity remains unproven: the current calculator documentation explicitly identifies some aggregate fixtures as synthetic rather than a complete original workbook reproduction.

## 14. Integration failure cases to handle explicitly

| Failure | Required handling |
| --- | --- |
| Invalid structure / duplicate line IDs / missing group | Reject request; keep editor state available for correction. |
| Incomplete rate/class/configuration | Save draft if structurally valid, but block financial publication/send. |
| Two editors save | Reject stale write token; preserve local edits for reconciliation. |
| Settings change during session | Explain configuration conflict; explicit refresh/reprice decision. |
| Labor class disabled | Explain unavailable class; never silently use another hourly rate. |
| Item becomes inactive | Keep historical/copied values; reject new unavailable selection; allow explicit replacement/custom-line workflow. |
| Quote sent while another user edits | Recheck editability under lock; reject later commercial save. |
| Quote content changed after publication | Mark publication stale; do not send its old total. |
| Client/network retries publish/send/accept | Return prior result for same action/key/payload; reject changed payload reuse. |
| Project handoff fails | Roll back acceptance and its financial effects. |
| Numeric precision exceeds destination | Reject or use an approved precision-preserving representation; never silently truncate intermediate evidence. |
| Unallocated project costs | Surface entered versus recovered amounts; no false complete customer total. |
| Old historical evidence incomplete | Preserve quality flag; never reconstruct original rates from today's settings. |
| Unsupported SERVICE/discount/supplier/currency input | Explicit unsupported/adapter requirement, not silent coercion into a different pricing model. |

Current JSON schemas are strict. Adding supplier, currency, source-version or engine-version fields requires a versioned contract change; extra fields will not simply pass through current validation.

## 15. Acceptance checklist for the calculator team

### Draft persistence

- [ ] Round-trip every input, override, group, image/reference and origin without loss.
- [ ] Verify first-save/null token, later tokens, concurrent saves and lost-response recovery.
- [ ] Verify incomplete drafts save without creating authoritative totals or lifecycle noise.
- [ ] Verify explicit configuration refresh versus session stability.
- [ ] Preserve unavailable Item inputs and surface disabled labor classes.

### Financial publication

- [ ] Server engine matches browser engine on approved fixtures and engine version.
- [ ] Whole/fractional quantities, zero/null, invalid inputs and margin/markup units are covered.
- [ ] Final payable, raw extensions, taxes and rounding adjustment reconcile exactly.
- [ ] Cost classification and embedded-IVU treatment are explicitly agreed.
- [ ] Travel/equipment/lodging appear once and unallocated costs block unsafe publication.
- [ ] Quote detail, lists, snapshots, exports and analytics show the same normalized summary.
- [ ] Item master records and ItemPriceHistory remain unchanged by quote overrides.
- [ ] Old PULSE BOM and LEGACY quotes keep their established calculations.
- [ ] Draft edits after publication invalidate the publication/review relationship.

### Lifecycle and history

- [ ] Review/send binds to exact content, settings, policy and source document identity.
- [ ] Changing Item/class/settings/client after send cannot change the sent presentation or money.
- [ ] Revision has a new Quote ID and copies original inputs/configuration evidence.
- [ ] Draft revision does not supersede the sent offer; replacement send does.
- [ ] Accept is atomic with project link/budget and retry-safe.
- [ ] Family counts, pipeline, win rate and weighted margin match the example above.
- [ ] Generated proposal and accepted project refer to the same accepted calculation evidence.
- [ ] Incomplete historical records remain identifiable rather than assigned guessed costs.

### Deployment

- [ ] Builder migration and canonical lifecycle migration are tested independently and together.
- [ ] Rehearse against isolated/restored data; verify permissions and preservation checks.
- [ ] No automatic conversion/deletion of existing QuoteItems, revision JSON or legacy financials.
- [ ] Audit scope includes send/revision/accept endpoints, imports and alternate editors, not just the new UI.
- [ ] Scope/quantity/performance tests cover realistic large estimates within the payload limit.
