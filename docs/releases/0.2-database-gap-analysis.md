# Pulse 0.2 database comparison

Reviewed: 2026-09-24. Assessment and proposed migration plan; no database or
application changes were made for this review.

## Conclusion and evidence

Keep PostgreSQL, Prisma and MinIO. The 0.2 guides describe an additive expansion
of the existing lifecycle database, not a replacement database or a new tenancy
architecture. The largest work is supplier sourcing, complete commercial
snapshots, content-bound review/proposal records, and document versions.

- [0.2 design](0.2.0-design.md), especially sections 3.3–3.6 and 9.
- [0.2 implementation map](0.2.0-implementation-plan.md), which corrects the
  design's 0.1.1 baseline to 0.1.2.
- [Earlier baseline review](0.2-baseline-review.md), used as historical context.
- [Current Prisma schema](../../apps/api/prisma/schema.prisma), current service

## Infrastructure that stays

[Development Compose](../../compose.yaml) uses PostgreSQL 16.14 by default,
database/schema `pulse`, a persistent PostgreSQL volume, and localhost-published
database access. [Production Compose](../../compose.production.yaml) keeps
PostgreSQL on the internal backend network with explicit persistent volume
names. The API uses Prisma 7.9.0 with the PostgreSQL adapter; the web tier does
not need database access.

The production configuration separates the runtime database identity from the
migration identity. Retain that boundary and verify grants on new tables and
sequences. [Role provisioning](../../apps/api/scripts/database/provision-roles.ts)
already grants default privileges for objects created by the migration role.
Those configured production permissions were not audited on this local DB.

MinIO remains the binary store. PostgreSQL holds file metadata, ownership,
checksums, source references and version relationships. Proposal generation
adds a rendering workload, but the guides do not require another database,
Redis, a PostgreSQL major upgrade, or a separate schema per customer.

## Integrity work that adding tables will not solve

1. **Historical reads and locks:**
   [workService.ts](../../apps/api/src/lib/services/workService.ts) currently
   prefers the live client name and current contact/site in `toQuoteRecord`.
   `updateQuoteProposal` has no sent-lock check. Expand commercial write guards
   and historical read selection alongside snapshot storage.
2. **Review → generation → send consistency:** a draft can change inside one
   revision number. All three actions must identify the same content version;
   send must atomically reject stale approval or generated output. Do not keep
   a DB transaction open during PDF rendering/upload.
3. **Exact evidence references:** price observations and generated proposals
   must reference a specific document version, never whatever version is
   currently selected for a family. Historical missing values must remain
   identifiable as missing rather than being filled from today's master data.
4. **Deletion semantics:** existing schema relations include cascading deletes
   from Client to Project/Invoice and from lifecycle records to documents.
   Review hard-delete paths and retention constraints before claiming durable
   commercial immutability. This is a schema risk, not evidence of data loss.
5. **Permissions:** extend existing `AccessRole`/`RolePermission` records and
   shared contracts. Reconcile `quotes:write` with the draft's proposed names.
   Internal-cost permissions must filter API, snapshot and export data, not
   only hide UI fields.

Recommended new access-path indexes include supplier/item lookups and dated
price history, reviewer/pending queues, user/unread notification queues,
quote/content artifact lookups, family/version uniqueness, and active deadline
queries. Confirm exact composite/partial indexes against implemented queries.

## Migration order and operational constraints

1. **Settle contracts:** agree snapshot ownership, status compatibility,
   date/time semantics, calculation rules and review policy. Preserve existing
   `Approved` and `Expired` meaning until a compatibility mapping is tested.
2. **Add integrity foundations:** content identity and nullable commercial
   snapshot fields; semantic date fields; feature flags and permission changes.
3. **Add document families and sourcing:** document version references before
   supplier price observations and quote-source snapshots depend on them.
4. **Add workflow/publishing:** reviews, notifications, template versions,
   frozen proposal inputs and generated artifacts; then transactional send
   validation and project/invoice snapshot transitions.
5. **Add remaining administration:** palettes, feedback and licensing state;
   integrate with the already implemented updater state model.
6. **Rehearse release:** upgrade a restored 0.1.2 fixture, reconcile data/files,
   verify runtime grants, and test rollback by restore. Test/document the 0.1.1
   compatibility path too. Deploy flags separately from schema installation.

Use small forward migrations after the existing seven. Keep released migration
files immutable; do not replay `legacy-migrations-pre-0.1`, reset the database,
or use `prisma db push` for an existing installation. See the existing
[migration runbook](../production/migrations.md).

There is an additional constraint in the current
[updater preservation check](../../services/updater/src/operations.mts): it
hashes protected rows using their original column set before/after migration.
New tables/columns and backfills limited to new columns can preserve that
evidence. Renaming/dropping old columns, rewriting statuses/categories, or
changing old `updatedAt` values can fail the check. Plan additive compatibility
fields first; legitimate changes to old data require a separately tested
migration/preservation procedure. Do not disable the check to make them pass.

The release generator requires the declared source-plus-target migration list
to match migration directories exactly. A 0.2 upgrade from 0.1.2 must name all
seven existing migrations as its source and the new migrations as its target.
No `docs/releases/0.2.0.json` upgrade contract currently exists. Extend
preservation/restore coverage for new historical tables in later upgrades.

## Inputs still needed and acceptance

The guides leave the Excel calculation specification, mandatory-review rules,
final business statuses, validity defaults/time semantics, unknown supplier
expiry handling, currency conversion policy, and document/rollout policies
unsettled. These determine parts of the final schema; the comparison above
does not treat recommendations as approved policy.

Acceptance should demonstrate unchanged historical records after master-data
edits, concurrent review/edit/send rejection, exact supplier/document lineage,
simultaneous document-version upload safety, retry-safe proposal generation,
date-boundary behavior, permission filtering, and readable history after flags
are disabled. Upgrade/restore tests must cover both PostgreSQL and MinIO links.
Those tests were not run in this read-only assessment.

## Critical follow-up review

Reviewed against current source and official PostgreSQL/Prisma/AWS guidance on
2026-09-24. Priorities below are recommendations, not newly approved scope.
Current behaviors are source findings; concurrency and crash scenarios are
inferred risks, not failures reproduced against customer data.

### Release blockers for the affected 0.2 workflow

**1. Commercial immutability is not enforced consistently.**
`workService.ts:1451` already locks the parent Quote for BOM edits and send;
that foundation is worth retaining. However, `updateQuoteProposal` has no
sent-lock check, and `updateQuote` can change title/client/contact/site without
the same commercial guard. Its transition checks read state before entering
the transaction. Historical reads also prefer some live directory values.
Use a shared transaction/lock protocol for commercial edits, recheck state
after acquiring the lock, and render historical values from the frozen
snapshot. Allow operational assignments separately. Merely adding snapshot
columns will not fix these paths. PostgreSQL locks protect particular rows;
they do not automatically enforce the whole domain workflow.
[PostgreSQL row locking](https://www.postgresql.org/docs/16/explicit-locking.html).

**2. Exact content identity cannot remain optional.**
The design calls `contentVersion` optional on Quote, while review and proposal
correctness depend on it or an equivalent immutable snapshot identity. A
reviewed draft can change without increasing `revisionNumber`. Make the
identity mandatory for the new workflow, increment it for every commercial
edit, and bind review, render input, generated artifact and send to it. If a
hash is used, define canonical serialization and schema version. Compare
identity atomically at send. Existing legacy records need an explicit
compatibility state, not invented approvals or reconstructed originals.

**3. Supplier cost is missing its purchasing basis.**
The proposed SupplierItem fields include cost, currency and minimum quantity,
but no explicit purchase unit, pack size or conversion to the catalog unit.
A $120 box of 100 connectors is not a $120-per-connector cost. Add a defined
price basis and snapshot the conversion used. Decide how quantity breaks,
freight and other landed-cost components affect estimating. They may be out of
scope, but unsupported cases must be explicit instead of silently mispriced.
This is a domain-model recommendation based on the field sketch.

**4. Financial policy is still underspecified.**
The current BOM paths default tax to zero even on taxable items. Supplier unit
prices may need more than two decimals: $0.004 per unit becomes zero at scale
two before multiplication. Decide input precision, rounding mode and stage,
currency/FX behavior, tax and labor/burden policy from real workbook fixtures.
Retain exact decimal arithmetic; audit existing Number conversions before
expanding precision. Store the calculation policy/version with commercial
snapshots. PostgreSQL numeric columns round to their declared scale.
[PostgreSQL numeric behavior](https://www.postgresql.org/docs/16/datatype-numeric.html).

**5. Retained files can still become inaccessible.**
`softDeleteDocument` marks a file deleted, and download/preview lookups require
`deletedAt: null`. Keeping the MinIO binary therefore does not ensure a sent
proposal or its pricing evidence stays available. Protect commercially
referenced versions from ordinary deletion or provide a deliberate authorized
historical-read path. Existing Client→Project/Invoice and lifecycle→document
cascades also deserve review. The normal client action currently archives;
this is not evidence that using Archive deletes invoices. Use restrictive
deletion rules where retaining the child is the business requirement.
[PostgreSQL foreign-key actions](https://www.postgresql.org/docs/16/ddl-constraints.html).

**6. Migration compatibility includes the updater, not just SQL.**
Original-column preservation hashes can reject legitimate old-status/category
rewrites and incidental `updatedAt` changes. Add compatibility fields first,
backfill new fields without mutating protected old fields, validate, then
switch readers. Defer destructive cleanup until old code no longer needs the
old shape. Any intentional old-data transformation needs reviewed semantic
reconciliation. Rehearse maintenance duration and restore as well as migration
success. This follows
[Prisma's expand-and-contract approach](https://www.prisma.io/dataguide/types/relational/expand-and-contract-pattern).

### Design corrections before freezing migrations

- **Document concurrency:** a Boolean current-version flag alone cannot prevent
  two simultaneous uploads becoming current. Use a unique family/version pair
  and either a partial unique index for the current member or a constrained
  family current-version pointer, with transactional replacement. A partial
  unique index enforces at most one current member, not that one must always
  exist. Define deletion/archival behavior explicitly.
  [PostgreSQL partial indexes](https://www.postgresql.org/docs/16/indexes-partial.html).
- **Dates:** existing date-only input is stored at noon UTC, and baseline
  timestamps use `TIMESTAMP(3)` without a time zone. That convention does not
  define the expiration of a quote. Use `date` for calendar-only deadlines and
  an explicitly modeled instant for send/review/expiry events; `timestamptz`
  is appropriate for instants. Store the business time zone/rule separately
  when it determines an end-of-day cutoff. Do not convert old timestamps
  without verifying their assumed zone.
  [PostgreSQL date/time semantics](https://www.postgresql.org/docs/16/datatype-datetime.html).
- **Database/file/job consistency:** upload currently writes MinIO before
  committing metadata and attempts cleanup on a caught DB failure. A process
  crash can bypass that cleanup. Generated proposals need persisted job/input
  identity, retry-safe object keys, publication state and reconciliation for
  abandoned objects. Persist local notifications in the workflow transaction;
  use an outbox for asynchronous work that must survive commit/crash boundaries.
  No external message broker is required just to implement this guarantee.
  [AWS transactional outbox guidance](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html).
- **Conflicting state fields:** flag `state` and `enabled` need one authoritative
  meaning; preferably derive enabled behavior from state/targeting. Likewise,
  keep internal approval, client acceptance and computed pricing expiry
  separate. The current meaning of stored Expired differs from the draft.
- **JSON ownership:** preserve JSON snapshots, but add schema versions and
  validation. Put identities used for relationships, access control and
  workflow queries into constrained relational fields. Do not make review
  evidence depend solely on generic Activity records; those have retention
  deletion, while commercial evidence has a different lifecycle.
- **Scope and tenancy:** single-installation product distribution does not
  imply multi-tenancy. Avoid optional workspace IDs scattered across models.
  Keep the infrastructure and deployment model stable while proving the full
  quote path. Palettes, licensing and rollout administration should not force
  a redesign of the core commercial model.

Recommended first gate: demonstrate estimate → review → generate → send →
revise on one real workbook example. Then change source master data, race an
edit against send, retry generation after a simulated crash, attempt deletion
of cited evidence, and upgrade/restore a 0.1.2 fixture. Passing ordinary CRUD
tests would not establish these guarantees. No such tests were run in this
follow-up review.
