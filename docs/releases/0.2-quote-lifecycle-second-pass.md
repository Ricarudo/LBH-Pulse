# Quote lifecycle — second implementation pass

Date: 2026-09-25. The first pass was committed as `224e1df` (`feat(quotes): establish lifecycle rules and freeze commercial edits`). Unrelated updater/UI work was preserved. This report describes the subsequent implementation, not a completed 0.2 rollout.

## Active application changes

New sends capture a validated commercial presentation alongside the existing exact financial evidence. Quote list/detail reads use evidence for the **exact current send**: quote ID, permanent number, revision number and sent timestamp must match. Ambiguous/missing evidence does not fall back to another revision.

Captured commercial facts include title, client name, contact, site, scope, preparation deadline, trades, proposal notes, lines and financial summary. Assignment, collaborators, current activity and project linkage stay live. Updating a shared lifecycle context through another stage no longer changes the displayed sent scope when a complete snapshot exists. A legacy revision's historical reader also retains the commercial snapshot when it is available.

The detail UI distinguishes a complete frozen snapshot from partial or unavailable historical evidence. Old snapshots are not fabricated from current master records: validated fields can be recovered, while the UI explicitly warns that other displayed facts still come from current records. The original legacy revision and Administrator undo endpoints remain unchanged until family activation.

## Staged family workflow

`quoteFamilyService.ts` implements transactions against the candidate sidecar schema. It is deliberately **not registered in the current HTTP controllers**. It supports:

1. Enrolling a new, unconverted, non-imported draft in a family. Historical backfill is excluded.
2. Creating a revision as a new Quote with new line IDs, a predecessor reference and an independent scope context. Prices and source values come from immutable stored evidence; send/outcome/readiness and preparation/follow-up dates start clear. Assignment/collaborators are inherited; tasks are not copied. Concurrent duplicate attempts return the existing draft.
3. Reading an exact family version. Drafts retain inherited client/contact/site facts rather than refreshing from changed directory records; an explicit link change selects different facts. Sending the revision preserves those facts too.
4. Sending the current draft with a current content token, current row timestamp, valid linked parties and known validity. Default validity is 30 workspace-local calendar days. Sending supersedes the previous offer atomically; drafting alone does not. Held or unresolved/unsupported review flows fail closed.
5. Accepting only the current, unclosed, valid sent offer and creating/linking its project in the same transaction. Acceptance discards any sibling draft and cancels pending sibling review. New-project scope is copied from the accepted snapshot into its own context. Project financial evidence records the exact content-snapshot ID.
6. Replaying an identical actor/action/key operation without duplicate rows/events/projects, and rejecting reuse of that key with a different request. Authorization is checked before replay. Family, quote and version locks serialize competing actions.

The existing handoff was extracted into a reusable transaction function. Its normal controller wrapper retains the existing behavior. Contact validation during handoff now uses that same transaction connection.

## Database and reporting foundations

The candidate SQL now guards managed sent/closed Quote content and line mutations, prevents sent versions from reopening and prevents closed version outcomes from being reset. Draft commercial changes increment a monotonic content token and invalidate readiness, including edits to their shared scope. Operational updates do not increment the token.

The family reader uses a consistent database snapshot. Its current pipeline projection takes the frozen current offer amount, or the active draft amount if no offer exists. It never sums both. Accepted families leave open pipeline. A separate current summary uses Decimal arithmetic and family counts for Home/work-list integration. Working and Awaiting response can overlap, while Open counts the family once. Needs Refresh remains an open-work condition and does not create an expiry/loss event.

The fixtures cover 1,000 sent → 1,200 replacement draft → 1,200 sent → accepted project at 1,200 before tax. They also cover concurrent revision creation, send/accept competition, retry behavior, failed-handoff rollback, immutable content, changed directory data and pricing validity.

## Activation is still a separate pass

Do not deploy the candidate schema or route existing revision/send calls to this service alone. Still required:

- Reviewed backfill, canonical Prisma integration, role grants, release metadata and deployment/rollback qualification.
- Family-aware HTTP DTOs, command/error mappings, one-family list rows, version navigation and revision/validity dialogs. The family-specific draft reader must accompany the new writer.
- Integration of all five Home widgets, client summaries, request/project references and period/as-of analytics. The current family summary is not a substitute for historical event projections or weighted accepted-margin calculations.
- Formal review/readiness actions, explicit directory refresh, selected document references and inherited file presentation. This staged service refuses sends for quotes with review records rather than pretending to implement review approval.
- Explicit rejection/cancellation/expiry, discard/renewal, erroneous-send correction and family archive commands, plus open-task/follow-up handling. Retire in-place revisions and reopening when the coordinated cutover activates.
- Adapt client merge/deletion and administrative repair paths to the managed-record guards; otherwise those legacy paths can correctly fail on frozen references. Add bounded/paginated projection queries and qualify scale before rollout.

The user-visible new-record revision workflow is therefore **implemented and integration-tested at the service layer, but not yet activated in the UI**.
