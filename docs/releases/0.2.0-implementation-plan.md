## Findings that affect the design

### Snapshot reuse requires stronger reads and write guards

`markQuoteSent` already records `versionSnapshot` in lifecycle event metadata;
it is not missing all snapshot behavior. However, `toQuoteRecord` still prefers
the live client display name and returns current contact/site data.
`updateQuoteProposal` writes notes without checking the sent lock. The existing
financial lock is therefore insufficient for the complete commercial lock in
the design. Inspect all commercial mutation paths, including context/detail
updates and revision creation, rather than adding guards only to BOM endpoints.

Use existing snapshots as historical evidence where complete. Never fill
missing historical values with today's master data and call them original.
Retain missing-data/provenance indicators for ambiguous records.

### Revision number alone cannot identify reviewed or generated content

A draft can change repeatedly within one revision number. The proposed
GeneratedProposal fields identify a revision/template, but need an immutable
render payload or snapshot reference plus content version/hash. A generated
file must remain reproducible in meaning even if the draft changes before send.

Proposed invariant: review, generation and send identify the same commercial
content version. At send, recheck the current version, applicable approval and
chosen generated artifact atomically. Reject stale selections with a clear
conflict response. Operational changes such as assignee/collaborators should
not invalidate approval unless the approved review policy says they do.

### Status semantics need a compatibility decision

The design separates business status and review state, but its suggested
business list includes Review, Changes Requested and Ready to Send. Choose
which is canonical and which is a displayed workflow state before persisting
overlapping sources of truth.

Current `updateQuote` requires a sent timestamp before moving to Expired.
The new draft assigns Expired primarily to an opportunity that was not viable
before completion/submission and uses Needs Refresh for stale sent pricing.
Do not bulk reinterpret old Expired records. Define legacy display/analytics
mapping, new transition rules and reviewed migration behavior first.

The proposed Approved → Accepted rename also affects approval/project
conversion, change orders, analytics, imports and historical revision display.
Internal approval and client acceptance must remain distinguishable regardless
of the final labels.

### Extend the existing document domain

The baseline already has stage-specific controlled categories, tag parsing,
a tag index, search behavior and inherited lifecycle files. Expand those
capabilities rather than introducing a parallel attachment system. The new
requirements are a shared type vocabulary, richer discovery, reclassification
and formal versions. Preserve existing category strings during mapping.

Price observations and generated proposals must reference exact document IDs,
not a family lookup that later resolves to a different current revision.
Enforce one current version with a database invariant and transactional
supersession. Keep deleted/archived family behavior explicit.

### Financial and permission contracts need completion

The current BOM path defaults line tax to zero even though taxable flags exist.
Tax applicability, rates, rounding, overhead and labor policy must come from
the Calculation Specification, not inference from UI labels.

The supplier snapshot field sketch omits some prose requirements: currency,
price-observation identity, exact source-document version and override
provenance. Include them in the final contracts. If supplier currency differs
from quote currency, either explicitly reject it or define and snapshot a
conversion rule/rate; never compare or total unlike currencies directly.

The current permission is `quotes:write`; section 4.1 also proposes
`quotes:update` and `quotes:status:manage`, which are absent from the section 5
matrix. Reconcile the permission inventory and existing role migration first.
`quotes:financials:internal` must control API response fields, revision data,
exports and documents as applicable, not just hide columns in React.

### Productization has external dependencies

There is singleton WorkspaceSettings configuration, not an established
multi-tenant workspace ownership model. Start rollout targeting with the
installation, roles and users unless real tenant isolation is explicitly added
to scope. Do not imply isolation through an optional workspaceId field alone.

Signed release discovery and license leases require issuer/service ownership,
protocols, keys, deployment channels and operational policies. Existing
digest-pinned installer manifests do not by themselves establish the proposed
signed updater protocol. Keep signing/private credentials outside application
images. The updater is a separate constrained component; the API receives no
unrestricted Docker socket.

| Milestone | Work and dependencies | Completion evidence |
| --- | --- | --- |

| M1 — Contracts and integrity | Snapshot field ownership; content versions; role migration; flags; status/date contracts; additive schema plan; token foundation | Existing history unchanged; concurrent mutation/send checks; API flag/permission tests; unresolved policies remain explicit |
| M2 — Estimating and sources | Excel specification/fixtures; suppliers and price observations; QuoteItem sourcing; labor/tax/burden; bundle UX; source documents | Reference estimates match approved rounding; changing catalog/prices cannot change old quotes |
| M3 — Review and lifecycle | Review decisions/invalidation; recipient notifications; draft/follow-up/validity UI; safe revisions and price refresh | Stale approvals rejected; deadline notifications deduplicated; historical status compatibility verified |
| M4 — Proposal publishing | Template versioning/editor; frozen payload; isolated HTML/PDF rendering; document families; generated history | Correct multipage output; exact quote/template/document lineage; unsafe template/network inputs rejected; retry-safe storage |
| M5 — Complete user journey | Atomic send validation; immutable historical display; record shell/palettes; contact profiles; client file discovery | Request → estimate → review → PDF → send → refresh → revision; source edits leave quote/project/invoice history stable |
| M6 — Productization | Update service/UI; licensing client/issuer integration; feedback; rollout administration | Signed/tampered/offline/grace cases; update backup/failure recovery; no customer data sent for licensing |
| M7 — Release acceptance | Representative upgrades; full workflow/security/browser checks; backup/restore; operator evidence | All design acceptance criteria traced to evidence; release artifacts and rollout defaults approved |

Milestones express dependencies, not a promise that every item runs serially.
Document families and supplier-source attachments must be available before
source snapshots need exact file versions. Productization protocol work and
shared UI tokens can progress independently of Excel formulas. Renderer
library selection requires a separate supported-version/security review when
implementation begins.

For rendering, use a persisted job/input identity and retry-safe artifact
creation rather than holding a database transaction open throughout a browser
render/upload. Revalidate content identity when associating the artifact with
the current send action. Render failure must not mark the quote sent.

Flag-off behavior must preserve access to existing historical records. Define
new-feature write/generation availability separately from historical read
access; migrations and retention cannot depend on UI activation.

## Upgrade and test strategy

Use 0.1.2 → 0.2.0 as the primary upgrade rehearsal because that is the verified
source baseline. The owner's requested 0.1.1 compatibility remains: either
support a tested direct path or document/test 0.1.1 → 0.1.2 → 0.2.0. Do not
promise a direct upgrade before validating migration and installer contracts.

Use small domain migrations and reviewed deterministic backfills. Preserve
LEGACY fields, revision JSON, lifecycle events, collaborators, existing
document/object links and ProjectQuote/expense data. Missing historical
identity remains missing/flagged unless original evidence proves the value.

Acceptance must include concurrent edit/review/send, failed or duplicate render
jobs, simultaneous document-version uploads, exact supplier/document lineage,
clock-boundary validity behavior, internal financial redaction, flag disabling
after data creation and migration/restore verification. Existing unit passes
do not substitute for these integration and release gates.
